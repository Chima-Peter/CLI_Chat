# Scenario SC-03 — Login with a taken nickname

**Feature:** FE-01 · **Use case:** UC-02

## Summary

A client attempts to log in with a nickname that is already being used by another authenticated client. The system identifies this conflict and re-prompts the client to enter a different nickname.

## Given

A client (User A) is connected and has received the login prompt ("Enter your nickname: "). Another client (User B) is already authenticated with a specific nickname (e.g., "Alice").

## When

User A sends a login request with the nickname "Alice".

## Then

The server detects that "Alice" is already taken, informs User A, and re-prompts User A to enter a valid nickname. User A remains unauthenticated.

| Step | Actor / system | Expected | Evidence |

| 1 | Client (User A) | Sends LOGIN request with nickname "Alice" | server/handle_conn.go:63 |

| 3 | Server | Detects nickname is taken | server/utils.go:116-131 |
| 4 | Server | Sends re-prompt message "Nickname is already taken. Enter a valid nickname: " | server/handle_conn.go:179 |

## Related code and tests

- `server/handle_conn.go`: Contains the `handleLogin` function which performs validation, including checking if a nickname is taken.
- `server/utils.go`: Contains the `isNickTaken` helper function that iterates over existing clients to verify nickname uniqueness.
