# Use case TC-01 — Switch context successfully (Feature QA-04)

## Summary

The user initiates a context switch to a specific room or friend to target subsequent messages. The system validates that the user has access to the specified context (is a member of the room or has the friend added) and updates the client session state accordingly.

## Actors and stakeholders

- **User**: The authenticated client initiating the context switch.
- **Server**: The component managing the client's current context state.

## Preconditions

- The user must be authenticated.
- If switching to a room, the user must be a member of that room.
- If switching to a friend, the user must have that friend.

## Data inputs and validation

- **`contextType`**: The type of context to switch to (`room` or `friend`). Parsed from user input.
- **`name`**: The name of the room or friend.
- **Validation**:
  - `name` must not be empty.
  - For `contextRoom`: The server verifies the user is a member of the room using `cl.roomByName` or resolving the room and checking `cl.my_rooms`.
  - Failure: If validation fails (room not found, user not in room), an error is returned to the client (`server/server.go:305`, `315`, `322`).

## Main flow (user- or operator-visible)

1. The user sends a command to switch context.
2. The server processes the `SWITCH_CONTEXT` request in `handle_conn.go`.
3. The server calls `s.SwitchContext` in `server/server.go`.
4. The server validates the context name and user's access.
5. The server updates the client's current context, room/friend, and sends a confirmation if successful.

## Code flow

1. **Entrypoint**: `server/handle_conn.go` receives `SWITCH_CONTEXT` action.
2. **Dispatch**: `server/handle_conn.go` calls `s.SwitchContext` with the appropriate parameters.
3. **Validation**: `server/server.go:301` performs initial trimming and validation.
4. **Context Check**: `server/server.go` verifies existence and access for room/friend.
5. **State Update**: Updates `cl.current_context`, `cl.room`, or `cl.current_friend`.

## Alternate flows

- **Context validation failure**: If the room/friend does not exist or user lacks access, an error message is sent to the client.

## Postconditions

- The client's session state is updated to reflect the new context. Subsequent messages are routed within this context.

## Errors and edge cases

- **Empty name**: Returns "usage: /switch <room|friend> <name>" error.
- **Room/Friend not found/accessible**: Returns "you are not in room: <name>" or similar error.

## Technical mapping

- `client` struct: Holds state (`current_context`, `room`, `current_friend`).
