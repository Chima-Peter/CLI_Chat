# Use case UC-06 — Invite user to room (Feature FE-02)

## Summary

The room owner invites another user to join their room. This action triggers a direct invitation to the target user and notifies the room owner upon success.

## Actors and stakeholders

- **Room Owner (Actor):** Initiates the invitation process.
- **Invitee (Actor):** The target user to be invited.
- **Server:** Manages room membership, invites, and notifications.

## Preconditions

- The Room Owner must be authenticated and connected to the server.
- The target room must exist.
- The Room Owner must have permission (i.e., be the owner) to manage invitations for the room.
- The Invitee must be a registered user on the server.
- The Invitee must not already be a member of the room.

## Data inputs and validation

The `SendRoomInvite` operation requires the following inputs, processed by the server:

- **`roomID` / `roomName`:** Used to identify the target room.
- **`memberID` / `memberName`:** Used to identify the target invitee.

### Validation Rules
1. **Room resolution:** The room must be resolvable via `s.resolveRoom(roomID, roomName)`. If not found, an error is returned.
2. **Authorization:** The actor must be the owner of the room (`room_data.owner.id == cl.id`). If not, "This action is reserved for only the admin!" error is returned.
3. **User resolution:** The invitee must be resolvable via `s.resolveUser(memberID, memberName)`. If not found, an error is returned.
4. **Membership check:** The invitee must not already be in the room. If `exists` in `room_data.members`, "X is already part of this room" error is returned.

## Main flow (user- or operator-visible)

1. The Room Owner sends an invitation request specifying the room and the user to invite.
2. The Server validates that the sender is the room owner.
3. The Server validates that the invitee exists and is not already a member.
4. The Server adds the room to the invitee's pending invitations.
5. The Server adds the invitee to the room's pending invitations map.
6. The Server notifies the Invitee about the invitation.
7. The Server notifies the Room Owner that the invitation was sent successfully.

## Code flow

1. **Entry:** `server.SendRoomInvite(cl, roomID, roomName, memberID, memberName)` is called (typically from `server/handle_conn.go`).
2. **Validation:**
   - Room resolution (`server/server.go:202`).
   - Ownership check (`server/server.go:208`).
   - User resolution (`server/server.go:213`).
   - Already member check (`server/server.go:219`).
3. **Action:** `room_data.SendRoomInvite(new_member, cl)` is called (`server/server.go:225`).
4. **Persistence/Notification:** `room.SendRoomInvite` (`server/rooms.go:279`) performs the state updates and notifications.

## Alternate flows

- **Room not found:** Request fails with error.
- **Not owner:** Request fails with authorization error.
- **User not found:** Request fails with error.
- **Already a member:** Request fails with error.

## Postconditions

- The room is added to the invitee's `room_invites` map.
- The invitee is added to the room's `invites` map.
- The Invitee receives a notification message.
- The Room Owner receives a confirmation message.

## Errors and edge cases

- Validation failures are caught and returned to the client using `cl.err(err)`.

## Technical mapping

- **Storage:** `room.invites` (map[id]*client), `client.room_invites` (map[id]*room).
- **Concurrency:** `room.mu` Mutex protects `invites` map access in `server/rooms.go:281-283`.
