# Scenario SC-02 — Member fails to delete room because not admin

**Feature:** FE-02 · **Use case:** UC-05

## Summary

A non-admin member attempts to delete a room. The system validates the ownership of the room. Since the member is not the owner (admin), the system sends an error message, but does not abort the deletion operation, resulting in the room being deleted regardless of authorization.

## Given

- A room `r` exists.
- The user `cl` is a member of room `r` but is **not** the owner of room `r` (`r.owner.id != cl.id`).

## When

- The user `cl` initiates a `DeleteRoom` action for room `r`.

## Then

- The system sends an error message: `"You cannot perform this action as you're not this room's admin."`.
- **Note:** The current implementation does not return after sending this error, so the deletion of the room proceeds.

## Step-by-step

| Step | Actor / system | Expected | Evidence |
| --- | --- | --- | --- |
| 1 | Member | Initiates `DeleteRoom` request for room `r`. | `server/rooms.go:216` |
| 2 | System | Validates ownership: `r.owner.id != cl.id`. | `server/rooms.go:222` |
| 3 | System | Sends error message because validation fails. | `server/rooms.go:223` |
| 4 | System | Proceeds to delete room (unexpectedly). | `server/rooms.go:226-248` |

## Related code and tests

- `server/rooms.go`: Contains the `DeleteRoom` method with the incomplete authorization check.

## Revision

- Initial draft: Added scenario SC-02 describing the authorization check and noting the missing return bug.

## Evidence index

- `server/rooms.go:222-224`: Implementation of authorization check in `DeleteRoom`, showing that `cl.err` is called but the function does not return, allowing the deletion to proceed.
